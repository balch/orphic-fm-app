# DJ App Android TV: Overscan + 10-Foot Density Scaling (2026-08-29)

- `DjLayoutMode.kt`: `LargeScreenMinWidth=900dp`/`MinHeight=500dp` gate `DjLayoutMode.LargeScreen` (docked-panel TV layout). A real 1080p Android TV reports **960x540dp** (density 2.0), not 1920x1080 — this is why the threshold is 900/500, not something bigger-looking.
- `LocalTvModeAllowed` (existing) gates LargeScreen eligibility (desktop: fullscreen-only). New `LocalTvDensityScale` (compositionLocalOf {1f}) carries the 10-foot density multiplier; DjAppScreen.kt multiplies `maxWidth`/`maxHeight` by it BEFORE calling `determineLayoutMode` — required because the density override (below) shrinks what BoxWithConstraints reports in dp, which would otherwise drop a real TV below the 900dp threshold and silently kill TV mode.
- `isTelevision()` (androidMain only, `Context.isTelevision()` in `TvMode.android.kt`): `UiModeManager.currentModeType == Configuration.UI_MODE_TYPE_TELEVISION` OR'd with `PackageManager.FEATURE_LEANBACK`. Verified on a real Chromecast with Google TV via `adb shell dumpsys uimode` (mCurUiMode 0x24 = TELEVISION|NIGHT_YES) and `adb shell pm list features` — both signals agree, no fallback edge case hit in practice.
- `tvDensityScale()` (androidMain, `TvMode.android.kt`): returns 1f off TV; on TV, `LocalConfiguration.current.screenWidthDp / 720f` (720 = `TvDesignWidthDp`, the canonical 10-foot design canvas so 720p/1080p/4K all normalize the same). Applied in `MainActivity.kt`'s `setContent` via `CompositionLocalProvider(LocalTvDensityScale provides tvScale, LocalDensity provides Density(base.density * tvScale, base.fontScale))` — multiply into `density` only, NEVER `fontScale` (that's the user's own accessibility setting; doubling it is a real bug class).
- Overscan margin (`PlatformSafeArea.android.kt`): computed from **real physical pixels** (`LocalContext.current.resources.displayMetrics.widthPixels/heightPixels * OverscanFraction`) fed into the RAW-INT `WindowInsets(left, top, right, bottom)` constructor — NOT the Dp-based constructor. Verified via compose-foundation sources (`androidx.compose.foundation.layout.WindowInsets.kt`): the Int-constructor's `getLeft/Top/Right/Bottom` return the stored raw px value UNCONDITIONALLY, ignoring whatever `density` param is passed at query time; the Dp-constructor instead does `with(density) { leftDp.roundToPx() }` using the density active AT THE QUERY SITE (i.e. wherever `.windowInsetsPadding()` resolves it in the tree) — so a Dp-based inset silently changes size if a density override sits between construction and consumption. Use the Int/px constructor whenever a margin must be a fixed fraction of the *physical* screen regardless of Compose-level density scaling elsewhere.
- `DjPanelDock.kt`'s existing `OverscanFraction` (0.05f) padding (`maxWidth * OverscanFraction` inside its own local `BoxWithConstraints`) is *automatically* density-scale-invariant already, with zero changes needed — a fraction of a locally-measured dp box stays that fraction regardless of what density produced the box's dp value. Only add NEW density-sensitive-looking overscan margins via that same "fraction of local BoxWithConstraints" pattern when the margin is meant to apply unconditionally (tablets/desktop LargeScreen too); use the raw-pixel `WindowInsets` + `isTelevision()` gate pattern above when it must be TV-hardware-only ("phone/tablet behavior must be provably unchanged" was an explicit requirement here).
- `DjTvRail` (the TV nav rail, left edge) gets `.windowInsetsPadding(platformSafeAreaInsets().only(Top + Bottom + Start))` — deliberately excludes `End`: that edge borders the stage/DjPanelDock, not the physical screen, and DjPanelDock already reserves its own overscan margin there. Adding End too would double-inset (extra dead gap, not a crop bug, but wasted space) — watch for this "which edges are actually screen edges vs internal container boundaries" question whenever inset padding is added to one region of a multi-region TV layout.
- Verification path used: `./gradlew :apps:djapp:androidApp:compileOgDebugReleaseKotlin` (Android, real check per repo convention — metadata compile doesn't count), plus `:apps:djapp:shared:compileKotlinJvm` and `compileKotlinIosSimulatorArm64` to prove the androidMain-only additions don't ripple into other actuals. `DjLayoutRenderHarness.kt` (jvmTest) renders `DjPanelDock` directly, not `DjAppScreen`/`DjTvRail`/`MainActivity` — it's a good regression check for panel-dock geometry but does NOT exercise the isTelevision()/density-override/rail-inset code path (that's Android-actual-only); added a plain `DjLayoutModeTest.kt` (commonTest, no Compose scene needed since `determineLayoutMode` is a pure `Dp`-in function) to lock in the compensation math instead.

## DJ App TV Nav: Rail → Top+Bottom Bars (2026-08-29, follow-up)

- `DjTvRail.kt` (NavigationRail with a header slot for title+viz) was replaced by `DjTvTopBar.kt` (title, Play/Pause, a duplicate VIBE `EnumDropdown`, `VizDropdown`, Info) and `DjTvBottomBar.kt` (one toggle per dockable panel). Trigger for the rail's existence in the first place: `NavigationSuiteScaffold`'s DSL takes only items, so the title/viz selector needed a rail's header slot; two plain `Row`s need no such slot, so the rail's reason to exist goes away entirely.
- **Bottom bar order ≠ dock toggle-order.** `largeScreenPanels()` returns `[Pulsar, DJ, Mix, Horn, Timer]` (toggle/append order for `assignDock`'s alternating left/right placement), but the bar was asked to *mirror physical position* instead: DJ/Mix (left column) — Pulsar (centre) — Horn/Timer (right column). Added a separate `BottomBarOrder`/`bottomBarPanels()` in `DjTvBottomBar.kt` that just reorders the display list; it does NOT touch `dockedPanels`/`toggleDocked`, so slot assignment (still insertion-order-based) is completely unaffected by which order the buttons are drawn in.
- **Sizing "nav items bigger, panel density unchanged" was achieved two ways**, both scoped to avoid touching shared widgets used elsewhere: (1) bespoke bar chrome (Play/Pause, Info, the 5 toggle chips) is hand-rolled in the two new files with explicit bigger consts (28-30dp icons vs 24dp default, 13sp labels vs ~11sp `labelSmall`, 64-76dp `defaultMinSize` touch targets) — safe because nothing else calls these composables; (2) `VizDropdown` (shared between the phone header and the old rail) got **optional** `modifier`/`height`/`textStyle` params defaulting to its old literals (36.dp, `labelSmall`) — every existing call site is unaffected, only `DjTvTopBar` passes bigger values (44.dp, `labelMedium`). Did NOT add similar params to `EnumDropdown` (used by Pulsar's own VIBE/ROOT/SCALE row) — the top bar's duplicate VIBE selector reuses it at natural size instead, since the task explicitly wanted Pulsar's own dropdown left untouched and a size-parameterized widget felt like scope creep for one duplicate call site.
- **Docked/hidden visual state on the bottom bar reuses the exact existing convention** — `neonCyan` tint + `NavIndicatorColor` (from `DjAppBottomNav.kt`, `internal val`, same package) background wash when docked, `Color.White.copy(alpha=0.55f)` + transparent otherwise. No new theme colors needed; this is literally the same selected/unselected language the phone nav and old rail already used, just applied to "docked" instead of "current route".
- **Safe-area redistribution**: old rail took `Top+Bottom+Start` (excluding `End` since the rail's right edge bordered the stage, not the screen). New layout is `Column(topBar, Box(stage), bottomBar)`, so top bar takes `Top+Start+End` and bottom bar takes `Bottom+Start+End` — both bars now span full width so left/right ARE physical edges. `DjPanelDock`'s own `OverscanFraction` padding needed zero changes (it already reserves its own margin on all 4 sides of whatever box it's given, regardless of who's above/below it).
- **Render harness extended to prove the whole screen**, not just the dock: added `renderFullTvScreen()` to `DjLayoutRenderHarness.kt` — composes `Column(DjTvTopBar, Box(weight=1f){DjPanelDock}, DjTvBottomBar)` directly with preview features at 1280x720dp (the `tvDensityScale`-widened canvas, not the raw 960x540dp a real TV reports) using `ImageComposeScene`. Confirmed via the rendered PNGs: bars don't overlap the dock, dock fills exactly the remaining vertical space via `Modifier.weight(1f).fillMaxWidth()`, and docked/hidden tinting on the bottom bar is visually obvious at a glance.
- `PulsarUiState(vibe: Vibe)` has NO default — every custom `PulsarUiState(...)` in a preview needs an explicit `vibe`, easiest sourced as `PulsarViewModel.previewFeature().vibeList.first()` (backed by a private `previewVibe`, `vibeList = listOf(previewVibe)`).
