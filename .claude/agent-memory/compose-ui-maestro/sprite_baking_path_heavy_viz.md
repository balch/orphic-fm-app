# Sprite-Baking for Path-Heavy Visualizations

From the HeartbeatViz RenderThread fix, 2026-08-29.

- Skia falls back to CPU `TriangulatingPathOp` per live Path draw; N shapes drawn 2-3x each per frame dominates RenderThread cost (measured: 30 hearts x 3 Path draws = 96 triangulations/frame, ~12.4ms on Android TV/Mali). Fix: bake the composite appearance ONCE per distinct color into an offscreen `ImageBitmap`, then `drawImage(..., blendMode=Plus)` per instance — zero triangulation, cheap FillRectOp-class cost instead.
- Offscreen render recipe (commonMain-safe, resolves on JVM/Android/WASM/iOS): `ImageBitmap(w,h)` -> `Canvas(bitmap)` (import as `androidx.compose.ui.graphics.Canvas as SkiaCanvas` — collides with `androidx.compose.foundation.Canvas`) -> `CanvasDrawScope().draw(density, layoutDirection, skiaCanvas, Size(w,h)) { /* reuse existing DrawScope-extension draw helpers here */ }`. Explicitly clear first with `canvas.drawRect(..., Paint().apply{blendMode=Clear})` — don't rely on zero-init being guaranteed on every backend. Plain Canvas+Paint precedent with no CanvasDrawScope (procedural non-Path art): `AlbumArtRenderer.kt` in pulsar.
- `BlendMode.Plus` layers are associative/commutative under clamping: pre-compositing N Plus layers into one bitmap (also via Plus, onto transparent) then drawing that ONE bitmap with Plus reproduces the same accumulated color as drawing all N directly — this is what makes baking safe for an additive glow. Would NOT hold for normal SrcOver layers (baking would occlude/lose whatever's underneath).
- One shared bitmap can't be re-tinted via `colorFilter` if any baked layer must stay a fixed hue regardless of tint (e.g. a white rim on colored hearts) — colorFilter recolors everything. Bake one sprite PER color actually in use instead (`HashMap<Color, ImageBitmap>`; 6 duo colors here).
- A knob-controlled ratio between baked layers (e.g. glow alpha) must be baked into the pixels, so the cache has to rebake on that knob changing beyond an epsilon — in practice only fires while the knob is being dragged, not per frame.
- A `Stroke(width = k/pixelRadius)` ("constant physical width regardless of scale") can't survive baking then uniform scaling — it thins proportionally at smaller draw sizes. Checked empirically via render-harness screenshot at the smallest on-screen size, found visually indistinguishable even zoomed 4x for a faint glow-scaled rim in a busy additive scene — a real approximation on paper, a non-issue by eye here.
- Verification technique: `androidx.compose.ui.ImageComposeScene(w,h,Density(1f)) { @Composable {...} }` -> `scene.render().encodeToData()!!.bytes` -> write PNG -> `scene.close()`. Headless in jvmTest, no device needed. For A/B-ing an optimization: a THROWAWAY test with a frozen copy of the old drawing code next to the new code in one Canvas at several sizes/alphas/colors, then delete the test once satisfied — keep permanent render-regression fixtures (`DjLayoutRenderHarness.kt`-style) separate from one-off equivalence proofs.
